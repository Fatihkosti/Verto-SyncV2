# خطة إصلاح وتطوير فواتير Verto — النسخة المنقحة النهائية

**خط أساس الفواتير:** `Verto-v238-source-of-truth.zip`  
**قرار النطاق:** يُعتمد هذا الخط للفواتير حتى لو تقدمت النسخ اللاحقة في ميزات أخرى غير مرتبطة بالفواتير. عند التنفيذ تُدمج تغييرات الفواتير فقط مع أحدث Source of Truth، بعد فحص التعارضات، دون إعادة تحليل الميزات الأخرى أو استبدال تعديلاتها.  
**النطاق:** فواتير البيع، الشراء المحلي، الشراء الدولي، الدفعات، الصندوق، المخزون، العملاء والموردون، الاستلام والشحن المرتبطان بالفاتورة، التقارير، والمزامنة المرتبطة بهذه الدورة.  
**الهدف:** تثبيت حقيقة مالية واحدة قابلة للتتبع، ثم إضافة التحسينات فوق أساس لا يسمح بالنجاح الجزئي أو إعادة كتابة التاريخ.

---

## القرارات غير القابلة للتغيير

1. سياسة Verto التشغيلية للمخزون هي **آخر سعر شراء معتمد لكل الرصيد الحالي**.
2. لا يُستخدم `Weighted Average Cost` في أي مسار شراء أو استلام أو تقرير تشغيلي داخل Verto.
3. عند شراء محلي جديد، يصبح السعر الجديد سعر شراء الكمية القديمة المتبقية والجديدة كلها.
4. عند استلام شراء دولي، تصبح `Landed Cost` النهائية سعر شراء كامل الرصيد الحالي للصنف.
5. سعر البيع مستقل، ولا يتغير تلقائيًا مع سعر الشراء.
6. تكلفة المبيعات التاريخية لا تتغير لاحقًا؛ يحفظ كل بند بيع `unitCostAtSale` لحظة ترحيل الفاتورة.
7. الفاتورة والمخزون والدفعة والصندوق والتدقيق وحدث المزامنة عملية ذرّية محليًا.
8. الفاتورة المرحلة لا تُحذف ولا يُعاد كتابة أثرها المالي؛ التصحيح يكون بعكس موثق أو مستند لاحق.

> ملاحظة محاسبية: آخر سعر شراء هو سياسة الإدارة التشغيلية المعتمدة في Verto. إذا طُلب لاحقًا تقرير قانوني وفق معيار محاسبي مختلف، يُبنى له دفتر/عرض مستقل دون تغيير سياسة Verto التشغيلية.

---

## قواعد تنفيذ عامة

1. التنفيذ جلسة بجلسة وبالترتيب الوارد.
2. تبدأ كل جلسة من آخر Source of Truth ناجح للجلسة السابقة.
3. قبل الدمج مع نسخة أحدث، تُفحص تعارضات الملفات والمخطط والعقود فقط؛ تقدم الميزات الأخرى لا يلغي خط أساس الفواتير.
4. يمنع بدء التحسينات 252–255 قبل نجاح بوابة 251.
5. يمنع أي migration مدمّر أو `fallbackToDestructiveMigration` أو تخمين بيانات مالية تاريخية.
6. لا يجوز استخدام `Double` أو `Float` لتمثيل المال أو سعر الصرف أو حساب الإجماليات.
7. كل أمر مالي يمتلك `writeId/requestId` ثابتًا من أول محاولة حتى كل Retry.
8. حماية `isSaving` في الواجهة مطلوبة، لكنها ليست بديلًا عن قيود قاعدة البيانات والذرّية.
9. كل قاعدة عمل توضع في Domain/Data وتُختبر؛ الواجهة تعرض النتيجة ولا تنشئ حقيقة مالية خاصة بها.
10. أي فشل في بند واحد من الأمر المالي يعيد المعاملة المحلية كلها.
11. المزامنة لا تدخل داخل Transaction محلية؛ يُكتب Outbox داخل المعاملة، ثم تُرسل الأحداث لاحقًا بصورة قابلة لإعادة المحاولة.
12. كل تعديل أو إلغاء أو تجاوز يحتاج: المستخدم، الوقت الفعلي، وقت التسجيل، السبب، والقيم قبل/بعد.
13. كل جلسة تنتهي باختبارات موجهة، اختبارات الوحدات المتأثرة، بناء كامل مناسب، وملف `verification-invoice-FNN.md`.
14. يمنع الانتقال إذا بقي خطأ مالي P0 أو P1، حتى لو كانت الشاشة تعمل.

## 244 — تأسيس Money Core وتصحيح الشراء المحلي

### الهدف
إنهاء الحسابات العائمة وتوحيد السعر والكمية والإجمالي والتقريب بين الواجهة وDomain وقاعدة البيانات.

### التنفيذ
- إنشاء أنواع/قواعد مركزية قابلة للاختبار:
  - `Money(amountMinor, currencyCode)` أو تمثيل ثابت الدقة مكافئ.
  - `ExchangeRate(baseCurrency, quoteCurrency, scaledValue, scale)`.
  - `Quantity` دقيقة؛ صحيحة للأصناف القطعية، أو Decimal ثابت إذا كان الكسر مسموحًا.
- تخزين المال كقيمة صحيحة ثابتة الدقة، وتخزين سعر الصرف بدقة معلنة؛ يمنع `Double/Float`.
- تحديد قاعدة التقريب الواحدة: يحسب السطر بدقة كاملة، ويقرب عند الحد المالي المعتمد مرة واحدة، ويعالج فرق آخر وحدة بصورة حتمية.
- توحيد Parser للأرقام العربية/الإنجليزية ومنع القيم الفارغة والسالبة والصفر غير المنطقي.
- إزالة الحاجة لفحص `NaN/Infinity` من Domain بجعل النوع المالي لا يستطيع تمثيلهما أصلًا.
- شراء محلي: الإجمالي يستخدم `buyPrice` فقط.
- `sellPrice` اختياري ومستقل، ولا يدخل في فاتورة المورد.
- إلغاء fallback الذي يحول الكمية غير الصالحة إلى 1 أو السعر إلى 0.
- جعل حساب UI وDomain والتخزين يستدعي القاعدة نفسها.
- تثبيت ترتيب الخصم/الرسوم/الضريبة إن كانت موجودة، مع اختبارات تقريب وحدود قصوى.
- إضافة Constraints تمنع overflow والقيم خارج النطاق.

### اختبارات القبول
- 2 × 100 شراء + سعر بيع 150 = فاتورة مورد 200.
- كمية فارغة أو `abc` لا تتحول إلى 1.
- سعر شراء فارغ أو صفر يرفض الحفظ برسالة قرب الحقل.
- 3 × 0.1 لا ينتج خطأ Binary floating point.
- حساب نفس المسودة في UI وDomain يعطي نفس القيمة تمامًا.
- البيع يستمر باستخدام سعر البيع، مع حفظ تكلفة البيع منفصلة لاحقًا في 247.

### شرح طبيعي
هذه الجلسة تبني لغة واحدة للمال؛ بعدها لا تختلف الشاشة عن قاعدة البيانات بسبب نوع رقم أو تقريب.

## 245 — معاملة ذرّية ومنع السباق والتكرار المحلي

### الهدف
ضمان أن الفاتورة وكل آثارها تنجح مرة واحدة معًا أو تفشل كلها، حتى مع ضغط مزدوج أو عمليتين متزامنتين.

### التنفيذ
- إنشاء Command واحد واضح لكل عملية مالية، يقوده Coordinator/Repository واحد.
- وضع الكتابات المحلية التالية داخل Transaction واحدة على نفس `RoomDatabase`:
  - الفاتورة والبنود.
  - تخصيص الدفعة.
  - حركة الصندوق عند وجود دفع.
  - حركة المخزون.
  - حدث إعادة التقييم عند الحاجة.
  - سجل التدقيق.
  - سجل Outbox.
- استخدام Transaction API المناسبة لإصدار Room الفعلي الذي كشفه 243؛ يمنع افتراض API قبل فحص الإصدار.
- أي Failure أو affected rows غير متوقع يرمي خطأ ويعيد كل المعاملة.
- استبدال `return@forEach` والابتلاع الصامت للأخطاء بنتيجة صريحة.
- خصم المخزون باستعلام شرطي ذري؛ فحص عدد الصفوف المتأثرة إلزامي.
- منع Read-Then-Write غير المحمي في المخزون والصندوق.
- إضافة Unique Constraints محلية على `tenant/company + operationType + writeId`.
- تطبيع رقم فاتورة المورد الخارجية، وإضافة قيد يمنع تكراره لنفس المورد والمنشأة عند وجوده.
- كل حركة مشتقة تحمل `sourceType + sourceId + sourceVersion` لمنع تكرارها.
- `inventoryItemId` الصريح هو الحقيقة؛ مطابقة الاسم لا تستخدم كحل صامت.
- إذا تعذر جمع الكتابات في قاعدة واحدة، تُوقف الجلسة لتحديد Aggregate/Compensation صريح؛ يمنع الادعاء بذرّية زائفة.

### اختبارات القبول
- مخزون 3 وبيع 5 والسالب ممنوع: لا فاتورة ولا دفعة ولا صندوق ولا Outbox.
- فشل البند الثاني يعيد أثر البند الأول بالكامل.
- عمليتا بيع متزامنتان لآخر قطعة: تنجح واحدة فقط.
- إعادة `writeId` نفسه عشر مرات: أثر مالي واحد.
- فشل كتابة Outbox يعيد الفاتورة وبقية الآثار.
- السماح بالمخزون السالب يعمل فقط عند تفعيل السياسة وبسجل تدقيق.

### شرح طبيعي
نجاح الشاشة لا يكفي؛ النجاح الحقيقي هو أن تتفق الفاتورة والمخزون والصندوق والتزامن في معاملة واحدة.

## 246 — نموذج العملات والدفعات وفروق الصرف

### الهدف
حفظ حقيقة الفاتورة الأجنبية وحقيقة الصندوق المحلي وتخصيص الدفعات دون فقد سعر الصرف أو خلط العملات.

### نموذج البيانات

لكل فاتورة دولية تحفظ على الأقل:
- `transactionCurrencyCode`
- `functionalCurrencyCode` من إعداد المنشأة، وليس SDG hardcoded داخل Domain.
- `transactionAmountMinor`
- `invoiceExchangeRateSnapshot`
- `exchangeRateDirection`؛ وحدات العملة الوظيفية لكل وحدة من عملة الفاتورة.
- `exchangeRateTimestamp`
- `exchangeRateSource`
- `functionalAmountAtRecognitionMinor`

لكل دفعة تحفظ:
- عملة مبلغ المورد ومبلغه المسدد.
- سعر الصرف الفعلي واتجاهه وتوقيته ومصدره.
- القيمة الفعلية الخارجة من الصندوق بالعملة الوظيفية.
- تخصيص الدفعة إلى الفاتورة في جدول `PaymentAllocation` مستقل.
- الجزء المقابل من قيمة الفاتورة التاريخية بالعملة الوظيفية.
- فرق الصرف المحقق ربحًا أو خسارة.

### التنفيذ
- المحلي: عملة العملية = العملة الوظيفية، وسعر الصرف = 1.
- الدولي: المبلغ الأصلي لا يُستبدل بقيمته المحلية.
- يدعم الإصلاح الدفع بعملة الفاتورة مع سحب مكافئها من الصندوق الوظيفي.
- الدفع بعملة ثالثة يُرفض صراحةً حتى يبنى دعم مستقل له.
- رصيد المورد يغلق حسب مبلغ عملة الفاتورة المخصص، لا حسب قيمة الصندوق.
- عند اختلاف سعر الدفع عن الاعتراف، يسجل فرق الصرف المحقق في حدث مستقل.
- لا يُعاد حساب فاتورة تاريخية بسعر صرف حديث.
- ترحيل البيانات القديمة:
  - الاستنتاج مسموح فقط من حقول موثوقة.
  - السجلات غير القابلة للاستنتاج تحمل `legacyCurrencyStatus = UNKNOWN/REVIEW_REQUIRED`.
  - تمنع السجلات المجهولة من المجاميع، وتظهر في تقرير مراجعة.
  - يمنع افتراض عملة وظيفية وسعر 1 لسجل دولي مجهول.
- تحديث Room entities، Domain، mappers، DTOs، عقود المزامنة، PDF، وتفاصيل الفاتورة.

### اختبارات القبول
- 100 USD بسعر 2,500 تحفظ 100 USD و250,000 بالعملة الوظيفية.
- دفع 40 بسعر 2,500 ثم 60 بسعر 2,600 يغلق 100 USD.
- القيمة الخارجة من الصندوق = 100,000 + 156,000.
- فرق الصرف المحقق = 6,000 خسارة مقارنة بالقيمة التاريخية للجزء المسدد.
- إعادة فتح التطبيق والمزامنة لا تغير القيم التاريخية.
- سجل دولي قديم مجهول لا يتحول تلقائيًا إلى محلي.

### شرح طبيعي
مبلغ المورد يجيب «كم ندين؟»، وحركة الصندوق تجيب «كم دفعنا محليًا؟»، وفرق الصرف يشرح الفرق بينهما.

## 247 — سياسة آخر سعر شراء وتكلفة البيع وLanded Cost

### الهدف
تنفيذ سياسة Verto دون متوسط، مع منع تغير أرباح الماضي وتسجيل فرق إعادة تقييم المخزون الحالي.

### الشراء المحلي
- عند ترحيل شراء محلي جديد داخل Transaction:
  1. قراءة الرصيد والسعر الحاليين.
  2. إضافة الكمية المقبولة.
  3. جعل السعر الجديد `currentBuyPrice` لكل الرصيد الناتج.
  4. تسجيل `InventoryCostRevaluationEvent` يحفظ الصنف، الكمية القديمة، السعرين، فرق التقييم، المصدر، المستخدم والوقت و`writeId`.
- لا تعاد كتابة حركات البيع السابقة ولا تكلفتها.
- سعر البيع يبقى كما هو.

### البيع وتكلفة المبيعات
- عند ترحيل البيع يحفظ كل بند:
  - `unitSellPrice`
  - `unitCostAtSale = currentBuyPrice` لحظة البيع.
  - `lineRevenueSnapshot`
  - `lineCostSnapshot`
  - `grossProfitSnapshot`
- أي شراء لاحق لا يغير ربح فاتورة بيع سابقة.
- يسمح بهامش استبدال حالي منفصل بالاسم عن الربح المحقق.

### الشراء الدولي وLanded Cost
- الفاتورة الدولية لا تدخل المخزون عند الإنشاء؛ بوابة المخزون هي الاستلام المقبول فقط.
- تجمع تكلفة الوصول المقبولة: قيمة البضاعة، الشحن، الجمارك، والرسوم القابلة للرسملة.
- تحفظ عملة وسعر صرف كل تكلفة؛ التوزيع يتم بقيم وظيفية دقيقة.
- قواعد التوزيع الافتراضية:
  - قيمة البضاعة والرسوم النسبية حسب قيمة البنود.
  - الشحن حسب الوزن/الحجم عند توفره، وإلا حسب القيمة.
  - رسوم الصنف المباشرة تحمل عليه مباشرة.
  - التوزيع اليدوي يحتاج صلاحية وسببًا ويطابق الإجمالي.
- فرق التقريب الأخير يوزع بصورة حتمية ومسجلة.
- عند الاستلام الجزئي توزع تكلفة الجزء المقبول فقط، وتبقى البقية معلقة.
- بعد حساب `landedUnitCost` يصبح سعر الشراء الجديد لكامل الرصيد الحالي، مع حدث إعادة تقييم.
- إذا وصلت تكلفة مؤكدة بعد الاستلام، تُسجل `LandedCostAdjustmentEvent` مستقلة تعيد تسعير الرصيد المتبقي فقط؛ لا تعدل تكلفة مبيعات سابقة.

### اختبارات القبول
- 10 قطع بسعر 100 + شراء 10 بسعر 200 = 20 قطعة بسعر 200، بلا متوسط.
- يسجل فرق تقييم 1,000 للرصيد القديم، دون تغيير تكلفة المبيعات السابقة.
- بيع قطعة قبل الشراء الجديد يحتفظ `unitCostAtSale = 100` بعد تغير السعر إلى 200.
- شراء دولي لا يزيد المخزون قبل الاستلام.
- مجموع Landed Cost الموزع يطابق إجمالي التكلفة المقبولة تمامًا.
- الاستلام الجزئي لا يحمل المقبول تكلفة الجزء غير المستلم.

### شرح طبيعي
السعر الجديد يعيد تسعير الرصيد الحالي، لكن تكلفة البيع القديمة تُقفل لحظة البيع ولا تتحرك معه.

## 248 — دورة حياة الفاتورة والعكس والتدقيق والصلاحيات

### الهدف
منع إعادة كتابة التاريخ وضمان أن الإلغاء يعكس الأثر الأصلي نفسه، لا قيمة محسوبة حديثًا.

### النموذج
- الحالة المالية المخزنة: `DRAFT / POSTED / VOID`.
- حالة الدفع منفصلة ومشتقة: `UNPAID / PARTIALLY_PAID / PAID`.
- `OVERDUE` مشتقة من الاستحقاق والرصيد، وليست حالة مخزنة متعارضة.
- طريقة الدفع منفصلة عن حالة الفاتورة.

### التنفيذ
- `DRAFT` قابلة للتعديل ولا تحرك مخزونًا أو صندوقًا.
- `POSTED` غير قابلة لإعادة كتابة البنود المالية.
- بنود الفاتورة المرحلة تحتفظ بلقطات الاسم وSKU والوحدة والأسعار والكمية والتكلفة؛ تعديل الصنف لاحقًا لا يغير المستند التاريخي.
- التعديلات الوصفية الآمنة تحدد بقائمة صريحة وتدخل Audit Log.
- التغيير المالي بعد الترحيل يتم بـ Void + Replacement، أو Return/Credit/Debit Note في 252.
- `Void` ينشئ Reversal Events مرتبطة بالأصل؛ يمنع الحذف الصلب.
- العكس يستخدم الحركات التاريخية الأصلية: الكمية، التكلفة، حركة الصندوق، التخصيصات وفروق الصرف.
- إذا وجدت دفعات، تُلغى تخصيصاتها وتتحول لرصيد أو رد وفق اختيار صريح؛ يمنع اختفاؤها.
- الفاتورة المرتبطة باستلام أو شحنة لا تُلغى بما يكسر السلسلة؛ تعكس العمليات التابعة بالترتيب أو يمنع الأمر.
- إضافة Optimistic Version لمنع تعديل جهازين للفاتورة نفسها.
- صلاحيات منفصلة: الترحيل، التعديل الوصفي، تجاوز المخزون، اعتماد سعر الصرف، توزيع Landed Cost يدوي، وVoid.
- كل استثناء يحتاج سببًا إلزاميًا وسجل قبل/بعد.

### اختبارات القبول
- إلغاء بيع يعكس المخزون والصندوق والتخصيصات مرة واحدة.
- إلغاء شراء دولي كاش يعيد القيمة المحلية الفعلية المدفوعة.
- إعادة Void بنفس `requestId` لا تنشئ عكسًا ثانيًا.
- فاتورة مدفوعة لا تُلغى دون معالجة الدفعة صراحةً.
- تعديلان متزامنان: يقبل إصدار واحد ويرفض القديم برسالة Conflict.
- لا يمكن حذف أثر مالي Posted.

### شرح طبيعي
لا نمسح الماضي؛ نربط به حركة عكس تشرح من فعل ماذا ولماذا وما الذي عاد فعليًا.

## 249 — المزامنة المالية وOutbox/Inbox ومنع التعارض

### الهدف
تحقيق مزامنة قابلة لإعادة المحاولة دون تكرار الأثر أو اعتماد Last-Write-Wins على بيانات مالية مرحلة.

### التنفيذ المحلي
- قاعدة البيانات المحلية هي مصدر العرض والحالة Offline-first.
- كل Transaction مالية تكتب Outbox Event داخل المعاملة نفسها.
- Outbox يحتوي `eventId`, `writeId`, `aggregateId`, `aggregateVersion`, `operationType`, `payloadVersion`, `createdAt`, `syncState`.
- الإرسال At-least-once؛ الأثر Exactly-once يتحقق بالـ idempotency وUnique Constraints.
- Inbox يسجل الأحداث المستلمة لمنع تطبيق الحدث نفسه مرتين.
- آلية الخلفية الحالية تعيد المحاولة بـ backoff، وتحافظ على ترتيب أحداث Aggregate الواحد.

### عقد الخادم
- Unique Constraint على `tenant/company + operationType + writeId`.
- الخادم يعيد النتيجة السابقة عند تكرار الطلب نفسه.
- Posted/Voided aggregates لا تستخدم Last-Write-Wins.
- Draft يسمح بتعارض مضبوط عبر `aggregateVersion`.
- الأحداث التابعة لا تطبق قبل الأصل؛ تحفظ أو تعاد محاولتها بوضوح.
- Void/Reversal يرسل حدثًا، لا حذفًا صامتًا.

### توافق الإصدارات
- أولًا يحدّث الخادم لقبول الحقول الجديدة مع استمرار قبول القديم.
- ثم يصدر التطبيق الذي يقرأ القديم والجديد ويكتب العقد الجديد.
- بعدها ينفذ Backfill الموثوق.
- أخيرًا تُشدد القيود بعد اختفاء العملاء القديمة المدعومة.
- كل Payload يحمل `schemaVersion`، مع Contract Tests للإصدارين خلال الانتقال.

### سياسة التعارض
- `DRAFT`: optimistic merge/version conflict واضح.
- `POSTED/PAID/VOID`: لا دمج حقول؛ يُقبل تسلسل أحداث صالح فقط.
- تعارض مالي غير قابل للحل يدخل `REQUIRES_REVIEW` ولا يُسوّى تلقائيًا.
- وقت الخادم مرجع الترتيب، مع الاحتفاظ بـ `occurredAt` و`recordedAt`.

### اختبارات القبول
- Offline create → retry → sync عشر مرات: فاتورة وحركات واحدة.
- انقطاع الرد بعد نجاح الخادم ثم Retry: يعيد النتيجة نفسها.
- وصول Payment قبل Invoice لا يضيع ولا يطبق على سجل مجهول.
- جهازان يعدلان Draft: يظهر Conflict مضبوط.
- جهازان يحاولان Void: عكس واحد فقط.
- عميل قديم وجديد يعملان خلال نافذة التوافق دون إسقاط حقول مالية.

### شرح طبيعي
الشبكة قد تكرر الرسالة؛ النظام الصحيح يتوقع ذلك ويجعل التكرار بلا أثر إضافي.

## 250 — التقارير والمطابقة والتشخيص

### الهدف
تحويل البيانات المصححة إلى تقارير قابلة للمراجعة وكشف أي اختلاف بين الفواتير والمخزون والصندوق.

### التنفيذ
- منع أي `SUM` لمبالغ بعملات مختلفة دون تحويل إلى العملة الوظيفية المحفوظة.
- التقارير المحلية تستخدم snapshots التاريخية، لا سعر صرف اليوم.
- كشف المورد الدولي يعرض أصل الفاتورة، المدفوع، المتبقي، النقد المحلي، وفرق الصرف.
- الربح المحقق يستخدم `unitCostAtSale` التاريخية.
- هامش الاستبدال يستخدم السعر الحالي ويُسمى منفصلًا.
- استبعاد Void، واحتساب Reversals/Returns دون محو الأصل.
- تحديث PDF والمشاركة لإظهار العملة وسعر الصرف والقيمة الوظيفية عند الحاجة.
- إضافة فحوص مطابقة:
  - إجمالي الفاتورة = المخصص + المتبقي بعملة الفاتورة.
  - إجمالي الدفعات = تخصيصات + رصيد غير مخصص.
  - الصندوق = مجموع الحركات غير الملغاة.
  - كمية الصنف = الافتتاح + مجموع الحركات.
  - قيمة المخزون التشغيلية = الرصيد الحالي × آخر سعر شراء.
  - كل حدث مالي محلي يمتلك Outbox أو حالة Sync نهائية.
- تقرير `Data Quality` للسجلات القديمة مجهولة العملة أو الهوية.
- إضافة فهارس بعد فحص Query Plans.

### اختبارات القبول
- 100 USD + 500,000 SDG لا تظهر 500,100.
- أرباح فاتورة قديمة لا تتغير بعد شراء بسعر جديد.
- نتيجة كل مطابقة صفر في قاعدة سليمة.
- فساد اختباري متعمد يظهر في تقرير المطابقة.
- PDF يعرض العملة الصحيحة ولا يخلط مبلغ المورد بقيمة الصندوق.

### شرح طبيعي
التقرير لا يكتفي بعرض الأرقام؛ يجب أن يثبت أن الفاتورة ورصيدها والصندوق والمخزون متطابقة.

## 251 — الهجرات والاختبارات وبوابة الإطلاق

### الهدف
إثبات أن الإصلاحات تتحمل البيانات القديمة، الأعطال، المنافسة، والعمل Offline قبل بدء التحسينات.

### الهجرات
- تصدير Room schemas لكل إصدار مدعوم.
- اختبار كل مسار ترقية مدعوم إلى الإصدار الجديد، وليس آخر إصدار فقط.
- لا يثبت رقم Migration في الخطة؛ يعتمد الرقم المكتشف في 243.
- اختبار القيود والفهارس والبيانات بعد الترحيل، لا نجاح فتح القاعدة فقط.
- تشغيل الترحيل على نسخة قاعدة اختبار واقعية كبيرة.
- أخذ نسخة احتياطية ووضع مسار تعافٍ واضح.
- لا يسمح Downgrade مدمّر؛ النسخة الأقدم ترفض بأمان عند عدم دعم الرجوع.

### طبقات الاختبار
- Unit: Money، التقريب، ExchangeRate، totals، validation، Last Purchase Price، إعادة التقييم، Cost-at-sale وFX.
- Property-based/parameterized: ثبات الإجماليات وIdempotency.
- DB Integration: Rollback بعد كل خطوة، Constraints، الخصم الشرطي، والمنافسة.
- Migration: كل إصدار مدعوم مع بيانات محلية ودولية ومجهولة.
- Sync Contract: Offline، retry، out-of-order، duplicate، conflict، عميل قديم/جديد.
- UI/Instrumented: rotation، process death، double tap، الأخطاء قرب الحقول، RTL.
- End-to-end: الأنواع الثلاثة × الدفع × Post/Payment/Void/Receive/Sync.
- Performance: فاتورة كبيرة، كشف طويل، Migration وتقارير بحجم واقعي.

### سيناريوهات إغلاق إلزامية
1. بيع أكبر من المخزون والسالب ممنوع.
2. فشل منتصف Transaction.
3. بيعان متزامنان لآخر قطعة.
4. شراء محلي يعيد تسعير كامل الرصيد دون متوسط.
5. بيع سابق يحتفظ بتكلفته بعد تغير السعر.
6. شراء دولي لا يدخل المخزون قبل الاستلام.
7. استلام جزئي مع Landed Cost.
8. دفعتان دوليتان بسعرين مختلفين وفرق صرف صحيح.
9. Void بعد دفع جزئي.
10. Retry بعد نجاح الخادم وضياع الرد.
11. Migration لسجل دولي مجهول.
12. تقرير متعدد العملات ومطابقة كاملة.

### تحقق البناء
- اختبارات الوحدات للModules المتأثرة.
- اختبارات قاعدة البيانات والهجرة على جهاز/محاكي.
- Compile لكل Modules التابعة.
- `assembleDebug` أو مهمة البناء الكاملة المناسبة للمشروع.
- lint/static checks الحالية دون إضافة تعطيل جديد.

### بوابة الخروج
- صفر أخطاء P0/P1 مالية مفتوحة.
- كل سيناريوهات الإغلاق ناجحة.
- نتائج المطابقة صفر على قاعدة الاختبار.
- لا فقد بيانات في Migration.
- لا أثر مكرر بعد Retry/Sync.
- توجد خطة إطلاق ومراقبة وتعافٍ موثقة.
- تراقب بعد الإطلاق: فشل المعاملات، تراكم Outbox، التعارضات، أخطاء Migration، وفروقات المطابقة، دون تسجيل بيانات مالية حساسة كاملة.

### شرح طبيعي
هذه بوابة إثبات؛ لا نضيف ميزات جديدة قبل نجاح النظام تحت الفشل والتكرار والبيانات القديمة.

# القسم الثاني — التحسينات بعد استقرار الأساس

## 252 — المرتجعات وCredit/Debit Notes

### الهدف
تصحيح البيع والشراء بمستندات مستقلة بدل تعديل الفاتورة الأصلية.

### التنفيذ
- `Sales Return / Credit Note` مرتبط ببنود البيع الأصلية.
- `Purchase Return / Debit Note` مرتبط ببنود الشراء الأصلية.
- منع إرجاع كمية أكبر من القابلة للإرجاع.
- إرجاع البيع يعيد الكمية ويحفظ تكلفة البيع الأصلية كمرجع العكس، ولا يغير `currentBuyPrice`.
- إرجاع الشراء يعكس العملية المحددة، ويعيد تحديد آخر سعر من أحدث شراء/استلام صالح غير ملغى عند الحاجة.
- وجود شراء أحدث يمنع الرجوع الصامت إلى سعر قديم.
- معالجة رد النقد، الرصيد، وتخصيص الدفعات بصورة ذرّية.

### اختبارات القبول
- لا تعديل للفاتورة الأصلية.
- Return جزئي مرتين لا يتجاوز الكمية الأصلية.
- إرجاع بيع لا يغير آخر سعر شراء.
- إرجاع آخر شراء يعيد السعر وفق أحدث حدث صالح.

### شرح طبيعي
المرتجع مستند جديد يشرح التصحيح ويحافظ على الفاتورة الأصلية بدل تعديلها أو حذفها.

## 253 — دورة المشتريات: PO → GRN → Supplier Invoice → Payment

### الهدف
ربط المطلوب والمستلم والمفوتر والمدفوع في دورة قابلة للرقابة.

### التنفيذ
- Purchase Order اختياري قبل الفاتورة.
- Goods Receipt/GRN يثبت الكمية المقبولة فعليًا.
- Three-Way Match بين المطلوب والمستلم والمفوتر.
- الفروقات تحتاج سببًا وصلاحية وحدود Tolerance.
- رقم فاتورة المورد الخارجي فريد لكل مورد/منشأة محليًا وخادميًا.
- الدولي: PO والفواتير مصادر للشحنة، والاستلام النهائي وحده يدخل المخزون.
- دعم الاستلام الجزئي والإغلاق الجزئي والمرفقات.
- منع الدفع لكمية غير مستلمة إلا Override موثق.

### اختبارات القبول
- تكرار رقم فاتورة المورد يُرفض.
- الاستلام الجزئي يبقي المتبقي مفتوحًا.
- فرق السعر أو الكمية يظهر ولا يعدل صامتًا.
- الدولي لا يدخل المخزون من PO أو الفاتورة.

### شرح طبيعي
هذه الدورة تقارن ما طلبناه بما وصل وما فوتره المورد قبل الدفع، فتمنع فروقات الكمية والسعر.

## 254 — UX موثوق ومسودات قابلة للاستعادة

### الهدف
تقليل أخطاء المستخدم وفقد العمل دون نقل قواعد العمل إلى Compose.

### التنفيذ
- حفظ Draft معقد في قاعدة محلية، لا داخل Bundle كبير.
- `SavedStateHandle/rememberSaveable` للحالة البسيطة اللازمة لاستعادة الشاشة فقط.
- مسح Draft بعد نجاح Post، وعدم مسحه بعد فشل الحفظ.
- تحذير عند الخروج مع تغييرات غير محفوظة.
- `isSaving` ومنع الضغط المكرر مع بقاء Domain/DB حماية أساسية.
- UDF: الحالة تنزل للواجهة، والأحداث تصعد إلى ViewModel.
- حالات Loading/Success/Error/Conflict/Offline واضحة.
- الشراء المحلي يبرز سعر الشراء ويفصل سعر البيع.
- الدولي يعرض المعادلة دائمًا: `100 USD × 2,500 = 250,000 Functional`.
- اختبار Process Death فعلي، لا Rotation فقط.
- الالتزام بنظام التصميم الحالي وRTL وإمكانية الوصول.

### اختبارات القبول
- قتل العملية يعيد المسودة دون فقد البنود.
- فشل Post يبقي المدخلات.
- نجاح Post يمسح المسودة مرة واحدة.
- الضغط المتكرر لا يكرر العملية.

### شرح طبيعي
الواجهة تحفظ عمل المستخدم وتقوده للبيانات الصحيحة، بينما تظل القواعد المالية محمية داخل Domain وقاعدة البيانات.

## 255 — التحليلات والتنبيهات التشغيلية

### الهدف
تحويل بيانات الفواتير النظيفة إلى قرارات، مع تسمية كل مقياس حسب أساسه الحقيقي.

### التنفيذ
- Aging للذمم المدينة والدائنة.
- DSO للعملاء وDPO للموردين.
- Purchase Price Variance.
- `Realized Gross Margin` من `unitCostAtSale`.
- `Current Replacement Margin` من آخر سعر شراء، كتقرير منفصل.
- Landed Cost variance حسب الشحنة والصنف.
- FX realized gain/loss حسب المورد والفترة.
- متوسط زمن الدفع وفروقات الموردين.
- تنبيهات: استحقاق، ارتفاع سعر، فرق صرف، فاتورة بلا استلام مطابق، تعارض يحتاج مراجعة.
- كل KPI يملك تعريفًا، مصدر بيانات، معادلة، عملة، وسياسة استبعاد Void/Returns.
- فحص أداء الاستعلامات والفهارس على حجم واقعي.

### اختبارات القبول
- الربح المحقق لا يتغير بشراء لاحق.
- هامش الاستبدال يظهر باسمه ولا يخلط بالربح المحقق.
- كل KPI لا يجمع عملات غير متجانسة.
- Void وReturns تؤثر وفق تعريف المقياس الموثق.

### شرح طبيعي
بعد تنظيف البيانات فقط، تتحول الفواتير إلى مؤشرات تساعد الإدارة دون أرقام مضللة أو ربح يتغير بأثر رجعي.

# تعريف النجاح النهائي

- كل مبلغ يستخدم نوعًا ثابت الدقة وقاعدة تقريب واحدة.
- لا توجد فاتورة ناجحة بأثر مخزون أو صندوق أو Outbox فاشل.
- عمليتان متزامنتان لا تبيعان نفس الكمية المحمية.
- نفس `writeId` لا ينشئ أثرًا ثانيًا محليًا أو خادميًا.
- كل فاتورة دولية تحفظ عملتها وسعرها التاريخي وقيمتها الوظيفية.
- الدفعات المتعددة تغلق رصيد العملة الأصلية وتسجل فرق الصرف.
- آخر سعر شراء يطبق على كامل الرصيد الحالي دون Weighted Average.
- إعادة تقييم الرصيد مسجلة، وأرباح المبيعات السابقة لا تتغير.
- الفاتورة الدولية لا تدخل المخزون قبل الاستلام المقبول.
- Void يعكس الحركات الأصلية ويحتفظ بالتاريخ والتدقيق.
- التقارير لا تجمع عملات مختلفة، ونتائج المطابقة صفر.
- Migration تحافظ على البيانات ولا تخمن السجلات الدولية المجهولة.
- المزامنة تتحمل Offline وRetry وOut-of-order وتعارض الأجهزة.
- دمج الخطة مع النسخ الأحدث يحافظ على تقدم الميزات الأخرى.
